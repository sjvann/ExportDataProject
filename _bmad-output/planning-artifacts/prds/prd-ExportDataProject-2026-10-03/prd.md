# PRD: 舊系統資料庫解析與系統分析文件

## 0. Document Purpose

這份 PRD 給產品、UX、架構與後續史詩拆分用。它定義分析師如何逐表看懂舊系統資料庫，以及 v1 必須交出的系統分析文件。詞彙以第 3 節詞彙表為準，後文不另造同義詞。功能需求編號 FR-1 起全域固定。推論而未經你確認的句子標為 `[ASSUMPTION]`，並彙整於第 9 節。

沒有既有的 UX 規格或正式系統分析書範本。產品現況（多資料庫讀取結構、外鍵、範例列，Web 仍以匯出 CSV 為首頁）只當作起點，不在本文重複實作方式。技術取捨、被放棄的方向與既有程式對照寫在同目錄的 `addendum.md`。

份量按內部工具、且分析包會進入升級案交付來寫。此讀者與交付情境已於 2026-10-03 確認。

## 1. Vision

系統整合與升級案接手的舊系統，常常沒有可讀的分析文件。資料庫還在跑，表名與欄名卻無法對上業務。本產品讓分析師連上這座舊系統資料庫，逐表對照結構、範例資料與關聯，寫下每個欄位的用途，再把已確認的理解收成一份系統分析文件：資料字典、實體關係圖、UML 類別圖，以及尚未確認的清單。

圖與字典來自同一份解析專案。分析師在資料表工作台裡確認的用途與關聯，就是文件裡的句子與線。起草可以建議用途，確認狀態只有分析師改得了。文件因此能同時滿足「很快看懂」與「交出去的內容分得清哪些已確認」。

既有的資料庫工具已經能從目錄畫出實體關係圖，也能在專案檔裡補上資料庫沒宣告的關聯。本產品要補上的是升級案真正卡住的兩步：用範例資料推想用途，以及把推想與已確認分開。分析包就是 v1 的系統分析文件。整庫匯出 CSV 只作為取樣手段，不是產品目的。

## 2. Target User

### 2.1 Jobs To Be Done

- 在沒有文件的升級案裡，不必離開資料表工作台，就能說明已打開的資料表各自負責什麼。
- 對著真實範例資料判斷一個欄位是識別碼、狀態、金額、日期還是備註，而不是只靠欄名猜測。
- 把看過的範圍畫成同事與客戶讀得懂的實體關係圖與 UML 類別圖，並能指著圖上的一張表回到證據。
- 交出的系統分析文件裡，已確認與仍屬草稿的內容分得開，接手的人不會把推測當成規格。
- 知道下一張該看哪張表，以及整座庫還剩多少未看。

### 2.2 Non-Users (v1)

- 需要日常備份、複製或排程傾印的資料庫管理員。v1 不為這項工作優化。
- 要在圖上改表結構並把變更寫回正式庫的設計者。
- 要從資料庫自動得到使用案例、作業流程或畫面規格的人。舊系統資料庫裡沒有這些。
- 需要多人同時編輯同一解析專案的團隊。v1 以一位分析師、一份解析專案為準。

### 2.3 Key User Journeys

主角為林安：系統整合案的系統分析師，接手一套仍在線上、沒有資料字典的舊系統。

**UJ-1. 林安連上舊庫，先知道這座庫有多大、從哪裡看起。**

- **Persona + context：** 林安第一天打開舊系統，只有一組唯讀連線，沒有上一任留下的文件。
- **Entry state：** 本機 Web 的解析專案尚不存在。
- **Path：** 建立解析專案，選擇資料庫類型並填入連線，讀取資料表清單。清單顯示表名、約略筆數、宣告關聯數、綱要或名稱前綴，以及確認狀態。他用前綴濾出疑似主檔的一群，打開其中筆數最多、被參照最多的一張。
- **Climax：** 他不用先匯出整庫，就知道表的數量、哪些群還沒看，以及建議先看的下一張。
- **Resolution：** 解析專案留在本機。隔天打開，清單與狀態還在。
- **Edge case：** 連線失敗或帳號不能讀目錄時，畫面指出失敗步驟，不建立一份空的、看起來像「沒有表」的解析專案。

**UJ-2. 林安在同一張畫面看懂一個欄位，並留下已確認。**

- **Persona + context：** 林安打開 `REG_MST` 這一類命名含糊的資料表，需要向開發說明「這欄到底是病歷號還是流水號」。
- **Entry state：** 已從 UJ-1 進入該資料表工作台。
- **Path：** 同一畫面看到欄位結構、少數範例列，以及只含這一張表與直接父表、子表的鄰居圖。他對照範例列寫下用途，再標成已確認。旁邊一欄是異動時間，他由未看直接標成略過。`[NON-GOAL for MVP]` 他點起草後，某一欄出現草稿用途與依據（欄名片段、型別、是否鍵、範例形狀），他再改寫並標成已確認。`[NON-GOAL for MVP]` 一條符合 FR-14 名稱規則、目錄中卻沒有的推測關聯出現在待決定清單；他接受之後，鄰居圖才畫上這條線。
- **Climax：** 該欄用途變成已確認，依據還在。他能指著範例值說明為什麼這樣寫。
- **Resolution：** 資料表確認狀態依欄位彙總更新。他按下一張未看的表繼續。
- **Edge case：** 起草找不到任何依據時，用途留白，依據寫成證據不足，確認狀態停在未看。他仍可自己寫下用途再確認。

**UJ-3. 林安把看過的範圍交成系統分析文件。**

- **Persona + context：** 週會要說明舊系統的掛號主檔與其直接相關表，開發與客戶都在場。
- **Entry state：** UJ-2 已累積若干已確認欄位。`[NON-GOAL for MVP]` 其中含至少一條已接受的推測關聯。
- **Path：** 他圈選這一群資料表，匯出分析包。包內有資料字典、這群表的實體關係圖、未確認清單，以及封面（專案名、資料庫類型與名稱、時間、範圍、已確認比例）。`[NON-GOAL for MVP]` 同一範圍另含 UML 類別圖。字典以確認狀態分開已確認與草稿。只有已接受的推測關聯出現在圖上。範例值是遮罩範例。
- **Climax：** 他打開圖與字典，對得上工作台裡那幾句已確認用途，且檔案裡沒有連線密碼。
- **Resolution：** 未看完的表列在未確認清單，會議把這些標成下週範圍，而不是默認已分析完。
- **Edge case：** 他尚未確認任何欄位就匯出時，分析包仍可產生，封面的已確認比例為 0，字典的用途欄為空或僅含草稿，圖只含宣告關聯。產品不阻擋匯出，也不把草稿印成已確認。

## 3. Glossary

- **舊系統資料庫** — 升級或整合案要解讀的既有資料庫。v1 類型為 SQLite、SQL Server、MySQL、Oracle。解析專案只讀取它。
- **解析專案** — 一份本機工作檔，綁定一座舊系統資料庫的連線與分析結果。關閉後再打開，用途、確認狀態與已接受的推測關聯仍在。
- **資料表** — 舊系統資料庫中的基礎表。檢視表不是資料表。
- **檢視表** — 由查詢定義的虛擬表。`[ASSUMPTION]` v1 可選擇列入盤點，預設不進入實體關係圖與 UML 類別圖。
- **欄位** — 資料表的一欄，含名稱、資料型別、長度或精度、可否空值、是否主鍵、是否外鍵、預設值。
- **宣告關聯** — 舊系統資料庫目錄中已存在的外鍵。父表、父欄、子表、子欄、約束名稱都來自目錄。
- **推測關聯** — 目錄中不存在的關聯。只存在解析專案裡。來源只有 FR-14 的兩種名稱規則，或分析師手動指定的兩欄。
- **待決定關聯** — 尚未被接受或拒絕的推測關聯。不畫進實體關係圖與 UML 類別圖。
- **已接受的推測關聯** — 分析師已接受或手動建立、因此可以畫進圖的推測關聯。
- **鄰居圖** — 以目前資料表為中心、只含一層父表與子表的實體關係圖。
- **模組** — 分析師為了出圖而圈選的一群資料表。可用綱要、名稱前綴或手動勾選產生。
- **實體關係圖** — 以 crow's foot 記法畫出的圖。實體是資料表，屬性是欄位，關係是宣告關聯或已接受的推測關聯。v1 唯一的 ER 記法是 crow's foot。
- **UML 類別圖** — 同一範圍的另一種投影。類別對應資料表，屬性對應欄位，關聯對應已畫入實體關係圖的關係，多重性對應基數。v1 的類別沒有操作。
- **基數** — 關係兩端的數量範圍，記成 `0..1`、`1`、`0..*`、`1..*` 或未明。
- **範例資料** — 從資料表讀取的有限列，用來觀察值的形狀。不是全表匯出。
- **用途** — 分析師或起草對資料表或欄位所寫的一句業務說明。
- **依據** — 用途所憑的觀察：欄名片段、資料型別、鍵別、關聯、範例形狀，或分析師自填的句子。
- **起草** — 依結構與範例資料產生用途草稿與依據的動作。起草不改變已確認的文字，除非分析師明確要求覆蓋。
- **確認狀態** — 欄位用途的四種狀態：未看、草稿、已確認、略過。
- **未看** — 尚無用途，且分析師未標成略過。
- **草稿** — 已有用途文字，分析師尚未標成已確認。起草寫入的狀態就是草稿。
- **已確認** — 分析師明示這句用途可以寫進系統分析文件。
- **略過** — 分析師明示此欄不需要業務用途（例如純稽核時間）。略過算解析完成，字典仍列出該欄。
- **資料表確認狀態** — 由欄位確認狀態彙總：未看、進行中、已確認。
- **分析包** — 一次匯出的系統分析文件，含封面、資料字典、實體關係圖、UML 類別圖、未確認清單。
- **資料字典** — 分析包中逐欄的表，欄位集合見 FR-20。
- **未確認清單** — 確認狀態仍為未看或草稿的資料表與欄位，以及仍在待決定關聯中的項目。
- **遮罩範例** — 保留值的形狀（長度、是否數字、是否含分隔符）但遮住識別內容的範例值。

## 4. Features

### 4.1 解析專案與盤點

**Description:** 林安以一份解析專案綁定一座舊系統資料庫，先看到完整清單與進度，再決定從哪張資料表看起（UJ-1）。讀取失敗時不得偽裝成空庫。再次讀取結構時，已寫下的用途與已接受的推測關聯保留。

**Functional Requirements:**

#### FR-1: 建立解析專案並唯讀連線

分析師可以建立解析專案，指定顯示名稱、資料庫類型與連線，並測試連線。實作 UJ-1。

**Consequences (testable):**
- 支援的資料庫類型僅為 SQLite、SQL Server、MySQL、Oracle。
- 測試成功後才允許進入盤點；失敗時保留尚未盤點的解析專案與錯誤訊息，清單不顯示為零張表。
- 錯誤訊息區分：連不上主機、認證失敗、沒有讀取目錄的權限、類型與連線內容不符。`[ASSUMPTION]` 訊息用繁體中文，並可附上驅動程式回傳的原始訊息。
- 整個 v1 對舊系統資料庫發出的語句限於目錄查詢與有上限的資料列查詢。不發出會改變資料或結構的語句。

#### FR-2: 盤點資料表

連線成功後，分析師可以看到舊系統資料庫的資料表清單。實作 UJ-1。

**Consequences (testable):**
- 每一列至少包含：表名、所屬綱要（若該類型有綱要）、約略筆數、宣告關聯數（作為父表或子表都計入）、欄位數、資料表確認狀態。
- 筆數查詢失敗時，該列筆數顯示為未知，其他表仍列出。
- `[ASSUMPTION]` 檢視表有獨立開關，預設關閉。開啟後檢視表出現在清單，標記為檢視表，資料表確認狀態不適用，且不能標成已確認。

#### FR-3: 從清單找到下一張要看的表

分析師可以搜尋表名、依綱要或名稱前綴篩選，並依筆數或宣告關聯數排序。實作 UJ-1、UJ-2。

**Consequences (testable):**
- 前綴比對為表名開頭，大小寫依該資料庫的識別字規則。
- 提供「下一張未看」。次序是目前篩選結果的目前排序：正開著一張表時，取該列之後第一張資料表確認狀態為未看的表；沒有正開著的表時，取排序後的第一張未看。分析師未另選排序時，依表名升冪，大小寫依該資料庫的識別字規則。沒有未看時明確告知，不另開已確認或進行中的表。
- 篩選不修改解析專案裡的確認狀態。

#### FR-4: 重新讀取時保留分析結論

分析師可以對同一解析專案重新讀取結構。實作 UJ-1。

**Consequences (testable):**
- 仍存在的資料表與欄位：用途、依據、確認狀態保留。
- 已消失的欄位：自工作台移除，並寫入分析包可選的「結構變更」附註，列出表名、欄名、消失時間。`[ASSUMPTION]` v1 只記錄消失與新增，不嘗試比對欄位改名。
- 新增欄位的確認狀態為未看。
- 已接受的推測關聯，若兩端欄位都還在，則保留；任一端消失則改列到未確認清單並標成端點已消失，不再畫進圖。

**Notes:**
- `[NOTE FOR PM]` 舊庫若在分析期間仍在改版，結構變更附註會決定文件是否可信。若升級案的舊庫已凍結，此附註可維持最小。

### 4.2 資料表工作台

**Description:** 看懂一張表的地方是資料表工作台，不是匯出流程。結構、範例資料與鄰居圖同時在場，用途寫在對應欄位旁邊（UJ-2）。確認狀態的規則保證起草不能把欄位改成已確認。

**Functional Requirements:**

#### FR-5: 單一工作台涵蓋結構、範例與鄰居圖

分析師打開一張資料表時，無須另一次操作就能看到欄位結構、範例資料與鄰居圖。實作 UJ-2。

**Consequences (testable):**
- 三塊資訊在同一頁。任一塊讀取失敗時，另外兩塊仍顯示，失敗塊說明原因。
- 從欄位上的外鍵、從鄰居圖上的表名，都能打開對方的資料表工作台，且目前表的未儲存用途會先被保留。

#### FR-6: 欄位結構足以對照目錄

工作台列出的每個欄位包含：欄名、資料型別、長度或精度與小數位、可否空值、是否主鍵、是否外鍵、參照的表與欄、預設值。實作 UJ-2。

**Consequences (testable):**
- 與目錄不一致時以重新讀取後的目錄為準，並沿用 FR-4 的保留規則。
- 沒有預設值或沒有外鍵時，該格為空，不以假值填滿。

#### FR-7: 範例資料有上限且服務推想

分析師可以載入該資料表的範例資料，用來觀察值的形狀。實作 UJ-2。

**Consequences (testable):**
- 預設 20 列，可調，上限 100 列。`[ASSUMPTION]` 這兩個數字尚未用真實舊庫核對。超過上限的要求被拒絕並說明上限。
- 查詢只取前 N 列，不先把全表拉到應用程式再截斷。順序是確定的：有主鍵則依主鍵升冪；沒有主鍵則依目錄回傳的穩定順序。這是供觀察形狀的確定樣本，不是隨機代表樣本。
- 空表顯示「沒有列」，欄位結構仍在，起草的依據不得捏造範例值。
- 工作台顯示原始範例值。分析包使用遮罩範例（見 FR-23）。

#### FR-8: 撰寫表與欄的用途

分析師可以為資料表與每個欄位撰寫用途，並改寫起草產生的文字。實作 UJ-2。

**Consequences (testable):**
- 用途為單段文字。`[ASSUMPTION]` 欄位用途建議不超過 200 字，超過仍可儲存，匯出時不截斷。
- 分析師編輯已確認的用途後，確認狀態回到草稿。
- 空白用途不能標成已確認。

#### FR-9: 確認狀態只有分析師推得動

分析師可以把有用途的欄位標成已確認，或把不需解釋的欄位標成略過。實作 UJ-2、UJ-3。

**Consequences (testable):**
- 允許的轉換：未看 → 草稿（寫入用途或起草成功）；未看 → 略過；草稿 → 已確認；草稿 → 略過；已確認 → 草稿（文字被改）；已確認 → 略過；略過 → 草稿（寫入用途）；略過 → 未看（清除略過且用途為空）。
- 禁止：未看 → 已確認；任何自動程序把草稿改成已確認。
- 略過的欄位沒有用途句子。若原先有草稿文字，標成略過時文字保留在解析專案但不進入字典的用途欄，字典該列狀態為略過。
- 資料表確認狀態規則：全部欄位為未看 → 未看；全部欄位為已確認或略過 → 已確認；其餘 → 進行中。

#### FR-10: 進度可見

盤點與工作台都顯示這份解析專案的進度。實作 UJ-1、UJ-2。

**Consequences (testable):**
- 進度為「資料表確認狀態為已確認的張數 / 資料表總張數」，檢視表不計入分母。
- 另顯示進行中張數與未看張數。
- 進度隨 FR-9 的彙總即時改變，不另設手動百分比。

### 4.3 實體關係圖與 UML 類別圖

**Description:** 視覺化回答「這些表如何相連」。工作時看鄰居圖，交付時看所選模組的實體關係圖與 UML 類別圖。兩種圖使用同一批已納入的關聯，避免圖與字典各說各話（UJ-2、UJ-3）。舊系統常常沒有外鍵；推測關聯補上這塊，但在被接受之前只留在待決定關聯。

**Functional Requirements:**

#### FR-11: 鄰居圖只畫一層

資料表工作台的鄰居圖包含目前資料表，以及經由宣告關聯或已接受推測關聯直接相連的父表與子表。實作 UJ-2。

**Consequences (testable):**
- 深度固定為一層。父表的其他子表、子表的其他父表不出現，除非它們也與目前表直接相連。
- 沒有任何關聯時，圖上只有目前這一張表，並說明「目錄中沒有宣告關聯」。
- 點選圖上其他表名會打開該資料表工作台。

#### FR-12: 基數來自鍵的性質，猜不了就標未明

實體關係圖與 UML 類別圖的基數依下列規則計算，兩種圖必須一致。實作 UJ-2、UJ-3。

**Consequences (testable):**
- 子欄視為唯一，僅當它是主鍵，或它上面有唯一索引。兩者皆無則視為非唯一。不依範例資料推翻這個判準。
- 宣告關聯的子欄可空且非唯一：子端 `0..*`，父端 `1`。
- 宣告關聯的子欄不可空且非唯一：子端 `1..*`，父端 `1`。
- 宣告關聯的子欄可空且唯一：子端 `0..1`，父端 `1`。
- 宣告關聯的子欄不可空且唯一：子端 `1`，父端 `1`。
- 父端是否一定存在列，v1 不查資料內容來推翻，父端維持 `1`。`[ASSUMPTION]` 不把父端畫成 `0..1`，因為那需要掃描事實表。
- 已接受的推測關聯若分析師未指定基數，基數為未明。分析師可以改成上述四種之一。
- 未明不得被畫成多對多，也不得在 UML 類別圖寫成 `*` 對 `*`。

#### FR-13: crow's foot 是實體關係圖的記法

實體關係圖以 crow's foot 表示基數，實體框顯示表名，並至少顯示主鍵與外鍵欄位。實作 UJ-3。

**Consequences (testable):**
- 分析師可切換屬性顯示：僅鍵、鍵加已確認用途、全部欄位。預設為僅鍵。
- 已確認用途以短語出現在屬性旁；草稿用途不出現在圖上。
- 宣告關聯與已接受的推測關聯以兩種可區分的線條呈現，圖例寫出兩者的詞彙表名稱。
- v1 不提供 Chen 記法，也不為第二套符號保留平行模型。

#### FR-14: 推測關聯先進入待決定，接受後才上圖

系統可以提出推測關聯；分析師也可以手動指定兩欄之間的推測關聯。實作 UJ-2。

**Consequences (testable):**
- 自動提出須同時滿足：子欄還不是任何宣告關聯的子欄；子欄與對方主鍵的型別家族相同（整數對整數、字串對字串，不要求長度相同）；名稱符合下面兩條之一。比較大小寫時，依該資料庫的識別字規則，與 FR-3 相同。
- 同名：子欄名稱與主鍵名稱相同。主鍵名稱在識別字規則下等於 `ID` 時，不使用這條，避免每張表的 `ID` 互相建議。
- 表名加主鍵名：子欄名稱等於「表名 + 主鍵名」，或等於「表名 + 一個底線 + 主鍵名」。表 `REG_MST`、主鍵 `ID` 時，必須建議 `REG_MSTID` 與 `REG_MST_ID`，不得建議 `REG_MST_NO` 或 `STATUS`。
- 不做模糊相似度，也不做包含比對。`STATUS` 不得因為名稱裡有相同片段而連到多張表。
- 同一對欄位只建議一次。拒絕後不再自動出現。
- 待決定關聯不出現在鄰居圖、模組實體關係圖與 UML 類別圖。
- 接受後成為已接受的推測關聯，之後的圖才畫出。
- 手動建立時必須指定兩端的表與欄。兩端缺一不能儲存。
- 接受、拒絕、手動建立與刪除都只改解析專案。操作前後，舊系統資料庫的外鍵數量不變。

#### FR-15: 以模組出整群的圖

分析師可以用綱要、名稱前綴或手動勾選定義一個模組，並查看該模組的實體關係圖。實作 UJ-3。

**Consequences (testable):**
- 圖中只含模組內的資料表。關聯的另一端不在模組內時，該關係不畫出，並在圖旁列出「連到模組外」的表名與欄名。
- 一個解析專案可以有多個模組。資料表可以同時屬於多個模組。
- 模組圖仍遵守 FR-12 與 FR-13。
- 未命名的「全部資料表」不是預設開啟的圖。分析師若仍要看，必須明確選擇，並在張數超過 40 時先顯示警告。`[ASSUMPTION]` 門檻 40 張。警告不禁止打開。

#### FR-16: UML 類別圖是同一範圍的投影

分析師可以把目前鄰居圖或目前模組另存為 UML 類別圖視圖。實作 UJ-3。

**Consequences (testable):**
- 類別名稱等於表名。屬性包含欄名與資料型別。主鍵與外鍵有標記。
- 只畫該範圍內、且已屬於實體關係圖的關係。多重性等於該關係的基數；基數未明時多重性標成未明。
- 不產生操作、介面、繼承或組合。多對多若在舊庫中是一張中間表加兩條宣告關聯，v1 保留這張中間表為類別，不自動折成關聯類別。`[ASSUMPTION]` 折疊中間表留到確認分析師真的需要物件模型之後。
- 在 UML 類別圖上不能編輯出一條實體關係圖沒有的關係。要新增關係必須走 FR-14，兩種圖一起更新。

**Feature-specific NFRs:**
- 鄰居圖在 30 張以內的直接鄰居時，於分析師可接受的單次等待內完成佈局。`[ASSUMPTION]` 目標是 5 秒內看到圖，逾時顯示已讀到的表並允許重試。
- 圖的佈局可以在工作階段中拖曳；`[ASSUMPTION]` v1 不要求重新打開解析專案後還原拖曳位置。匯出時使用當下佈局，若無拖曳則使用自動佈局。

### 4.4 依範例資料起草用途

**Description:** 起草把 UJ-2 的推想做成可覆核的草稿。它讀取的是這一張表的結構、關聯與有限範例，寫入的是用途與依據。它不是已確認，也不是聊天窗口。

**Functional Requirements:**

#### FR-17: 對一張表或一個欄位起草

分析師可以對目前資料表的全部欄位，或單一欄位，執行起草。實作 UJ-2。

**Consequences (testable):**
- 輸入只含：表名、欄位結構、與該表有關的宣告關聯與已接受推測關聯、FR-7 範圍內的範例資料、分析師已寫且狀態為已確認的同表用途（供用詞一致）。
- 不讀取未出現在工作台的其他表的範例資料，不讀取超過 FR-7 上限的列。
- 每個被起草的欄位得到一段用途與一條依據。依據必須引用至少一項真實觀察（欄名片段、資料型別、鍵別、關聯的對方表名、範例形狀）。
- 找不到任何觀察可引用時，不寫用途，依據為「證據不足」，確認狀態維持未看。
- 已確認與略過的欄位不被覆蓋。分析師若明確選擇「重新起草已確認欄位」，該欄回到草稿並換上新文字與新依據。
- 成功寫入草稿的欄位，確認狀態成為草稿。

#### FR-18: 起草失敗時工作台仍可手工分析

起草不可用時，分析師仍可完成 FR-8 與 FR-9。實作 UJ-2。

**Consequences (testable):**
- 失敗顯示原因：未載入範例資料、連線中斷、起草元件無回應。
- 失敗不清除既有用途與確認狀態。
- 起草預設不把範例資料送出本機。只有分析師另開一個明確開關時才允許外送，開關預設關閉。外送前必須先套用與 FR-23 相同的遮罩。是否必須在無外部網路時仍能起草，見開放問題 3。

**Notes:**
- `[NOTE FOR PM]` 範例資料可能含姓名、病歷號或身分證。開關的預設與 FR-23 的遮罩是同一項信任決策。若目標客戶的舊庫在隔離網段，沒有離線起草就等於此功能不存在。

### 4.5 分析包

**Description:** 分析包是 v1 的系統分析文件。它讓林安把一個模組或一組自選資料表交到會議上（UJ-3）。已確認、草稿與尚未看的範圍在文件裡彼此分得開。

**Functional Requirements:**

#### FR-19: 選擇匯出範圍

分析師可以匯出：目前資料表及其鄰居、一個模組，或手動勾選的資料表集合。實作 UJ-3。

**Consequences (testable):**
- 範圍至少一張資料表，否則不產生分析包並說明原因。
- 封面列出範圍內的表名、匯出時間、解析專案名稱、資料庫類型、資料庫名稱、進度（與 FR-10 同一套數字，分母改為本次範圍內的資料表張數）。
- 封面與檔內任何位置都不含連線字串與密碼。

#### FR-20: 資料字典的欄位固定

分析包內的資料字典對範圍內每個欄位有一列。實作 UJ-3。

**Consequences (testable):**
- 欄位固定為：表名、表用途、表的資料表確認狀態、欄名、資料型別、長度或精度、可否空值、主鍵、外鍵、參照表、參照欄、預設值、遮罩範例、用途、確認狀態、依據。
- 表用途只在該表第一列重複或每列都帶皆可，但同一張表的表用途文字必須相同。
- 確認狀態使用詞彙表四個詞，不使用同義詞（例如不用「完成」「核可」「AI 建議」）。
- 略過的列：用途為空，確認狀態為略過。
- 字典另附關聯表：父表、父欄、子表、子欄、種類（宣告關聯或推測關聯）、基數、是否已接受。待決定關聯不在這張關聯表，而在未確認清單。

#### FR-21: 匯出的圖與工作台是同一模型

分析包含該範圍的實體關係圖與 UML 類別圖，規則與 FR-11 至 FR-16 相同。實作 UJ-3。

**Consequences (testable):**
- 實體關係圖為可縮放的向量圖（SVG）。UML 類別圖同樣為 SVG。
- `[ASSUMPTION]` 另附一份同內容的圖檔（PNG），方便貼進既有報告書；PNG 無法取代 SVG 作為規格圖。
- 圖例包含 crow's foot、宣告關聯、推測關聯、未明基數。
- 抽查任一已接受推測關聯：工作台看得到、SVG 看得到、字典關聯表看得到。抽查任一待決定關聯：三處都看不到。

#### FR-22: 未確認清單隨包附上

每份分析包都包含未確認清單。實作 UJ-3。

**Consequences (testable):**
- 列出範圍內確認狀態為未看或草稿的欄位，以及一端落在範圍內的待決定關聯。
- 範圍內若沒有這類項目，清單仍存在，內容為「此範圍沒有未確認項目」，不得省略這個檔。
- 已確認比例不是 100% 時，封面直接寫出未確認的欄位數，不隱藏。

#### FR-23: 分析包裡的範例是遮罩範例

字典的範例欄使用遮罩範例。實作 UJ-3。

**Consequences (testable):**
- 先取至多三個相異的原始值，再各自遮罩。相異以遮罩前的原值比較。另外附上形狀描述：最大長度、是否全為數字、是否含日期分隔符。日期分隔符只認 `-`、`/`、`.`。
- 遮罩保留首尾各一字元（長度小於 4 則全部以符號代替），中間以固定符號代替。空值記為空，不變成遮罩字串。
- 分析師可對該次匯出打開「包含未遮罩範例」。預設關閉。打開時封面必須印出「本包含未遮罩範例資料」。
- `[ASSUMPTION]` v1 的遮罩是固定規則，不依個資類別改策略。它防止分析包被轉寄時直接露出完整識別值，不表示已完成去識別化。

**Feature-specific NFRs:**
- 匯出在本機完成，不依賴外部網路才能得到 SVG 與字典。

## 5. Non-Goals (Explicit)

- v1 不把變更寫回舊系統資料庫，也不產生「套用到正式庫」的結構變更腳本。
- v1 不產出使用案例圖、循序圖、活動圖、資料流程圖或畫面規格。
- v1 不做排程備份、整庫傾印、或與原廠備份工具比較速度。
- v1 不把起草擴成可對資料庫下任意查詢的對話介面。
- v1 不自動將任何欄位標成已確認，也不以已確認比例當作起草元件的優化目標。
- v1 的系統分析文件就是分析包。它不另保證符合尚未提供的政府機關或客戶章節範本。現在的規範是第 3 節、crow's foot，以及 FR-20 至 FR-22。日後若有章節範本，用同一份欄位填入，不建立第二份真相。
- v1 不證明法律或資安合規。遮罩範例不是去識別化合規聲明。
- v1 不支援多人同時編輯同一解析專案。
- v1 不新增第五種資料庫類型。
- v1 不把檢視表畫成實體。`[ASSUMPTION]`
- v1 不把中間表自動折成 UML 關聯類別。

## 6. MVP Scope

MVP 是 v1 裡最先釋出的一截，用來驗證「逐表工作台 + 已確認留得下來 + 字典與鄰居圖一致」。它不是另一個產品。

### 6.1 In Scope

- FR-1、FR-2、FR-3、FR-4
- FR-5、FR-6、FR-7、FR-8、FR-9、FR-10
- FR-11、FR-12、FR-13 的鄰居圖（含僅鍵 / 全部欄位兩種顯示）
- FR-19 的「目前資料表及其鄰居」與手動勾選
- FR-20、FR-22、FR-23
- 分析包中的鄰居範圍實體關係圖 SVG（FR-21 的實體關係圖部分）
- 跨切 NFR：唯讀、密碼不入包、重新開啟後用途仍在

### 6.2 Out of Scope for MVP

- FR-14 推測關聯、FR-15 模組、FR-16 UML 類別圖。原因：先證明宣告關聯的鄰居圖與字典可信，再補舊庫沒有外鍵時的線，以及第二種投影。三者都在 v1，緊接 MVP。已確認的提前條件：若第一座真實舊庫幾乎沒有外鍵，FR-14 改納入 MVP。在得知該庫的外鍵情況之前，FR-14 仍排在 MVP 之後。
- FR-17、FR-18 起草。原因：MVP 先讓分析師手寫用途，確認狀態規則先穩。起草在用途存得下來之後加入，避免一開始就辯論模型。
- 屬性顯示中的「鍵加已確認用途」、PNG、結構變更附註的完整呈現。MVP 的字典已含確認狀態與依據；圖上先不排文字。
- Chen 記法、多人協作、檢視表入圖、中間表折疊。與 v1 非目標相同，不是延後功能。

## 7. Success Metrics

**Primary**

- **SM-1**：林安完成一張資料表的結構閱讀、範例對照、至少一個欄位標成已確認，且全程留在資料表工作台。目標：不需要另開匯出頁或外部繪圖工具。驗證 FR-5、FR-7、FR-8、FR-9。
- **SM-2**：分析包抽樣的每一列，其確認狀態、用途與依據與當時解析專案一致。目標：抽樣 100% 一致。驗證 FR-20、FR-22。
- **SM-3**：鄰居圖上的每一條宣告關聯都能在目錄的外鍵中找到，基數符合 FR-12。目標：抽樣 100% 一致，且不存在目錄裡沒有、圖上卻畫成宣告關聯的線。驗證 FR-11、FR-12、FR-13。
- **SM-6**：未參與操作的讀者只看分析包，能指出哪些列是已確認、哪些列在未確認清單，且確認狀態為草稿的列不會被讀成已確認。驗證 FR-20、FR-22。

**Secondary**

- **SM-4**：連續使用下，資料表確認狀態為已確認的張數增加，且「下一張未看」打開的表確實是未看。驗證 FR-3、FR-10。
- **SM-5**：MVP 之後加入起草時，證據不足的欄位維持未看。目標：此類欄位被自動標成已確認的次數為 0。驗證 FR-9、FR-17。

**Counter-metrics (do not optimize)**

- **SM-C1**：已確認欄位數不得被起草或重新讀取自動拉高。自動變成已確認的次數必須維持 0。對應 SM-6：文件要分得清已確認與草稿，不是把已確認比例做高。
- **SM-C2**：不追求單張圖裡的資料表張數。預設成功畫面是鄰居圖。整庫一張圖能打開不算成功。
- **SM-C3**：不追求匯出列數、CSV 大小或壓縮率。範例資料超過 FR-7 上限不算更好。

## 10. Information Architecture

分析工作發生在本機 Web。既有的命令列匯出不承載 UJ-1 至 UJ-3。

- **解析專案首頁：** 建立或打開解析專案、連線測試、資料表清單、搜尋與前綴、進度、下一張未看、進入匯出。
- **資料表工作台：** 表用途、鄰居圖、欄位與確認狀態、範例資料、待決定關聯（v1 在 MVP 之後出現）、起草（v1 在 MVP 之後出現）。
- **模組：** 由清單勾選或前綴產生，打開模組實體關係圖與 UML 類別圖。MVP 沒有這個目的地。
- **匯出：** 選擇範圍、是否包含未遮罩範例、產生分析包。不是首頁的主行動。

主行動從首頁到工作台是「繼續下一張未看」，不是「匯出全部」。

## 11. Cross-Cutting NFRs

- **唯讀：** 任何功能對舊系統資料庫都不得改變資料或結構。驗證方式：操作前後外鍵與一張抽樣表的列數不變，且連線使用的敘述中不出現會寫入的指令。
- **可恢復：** 分析師確認用途後關閉程式，再次打開同一解析專案，該用途與確認狀態仍在。
- **機密：** 日誌、分析包、錯誤訊息不寫出完整連線字串與密碼。
- **規模：** `[ASSUMPTION]` 清單在 500 張資料表時仍可搜尋與篩選。不要求 500 張同時出現在一張圖上。
- **本機交付：** SVG 與資料字典的產生不需要外部網路。
- **語言：** `[ASSUMPTION]` 介面與分析包的固定標題使用繁體中文。表名與欄名維持資料庫原樣，不翻譯。

## 12. Constraints and Guardrails

### Safety

- 連線對象可能是仍在線上的舊系統。範例查詢必須有列數上限與逾時。`[ASSUMPTION]` 單次範例查詢逾時 30 秒，逾時則該表範例失敗、工作台其餘部分仍可用。
- 產品不提供「在圖上編輯並產生寫回腳本」的模式，避免與資料庫管理工具的編輯模式混淆。

### Privacy

- 工作台的原始範例值只供當下推想。分析包預設改為遮罩範例。
- 起草預設只在本機使用這些值。外送是選擇加入。
- 遮罩不宣稱符合個資法或 HIPAA。`[NOTE FOR PM]` 若這座舊庫的管理規定禁止分析師在畫面上看到原始識別值，必須改 FR-7，這會直接影響 UJ-2 的推想品質。

### Cost

- `[ASSUMPTION]` v1 不採按座計費或帳號體系。成本風險只來自分別把範例資料送到外部起草服務。預設路徑不產生這筆費用。

## 13. Decision Provenance

系統分析文件的可信度來自分得清誰下的結論。

- 確認狀態為已確認的用途，作者只可能是分析師的明示動作。
- 草稿的作者是分析師手寫，或起草。字典的依據欄必須讓讀者看出這句話憑什麼寫下。
- 宣告關聯的作者是舊系統資料庫目錄。推測關聯的作者是分析師的接受或手動建立。待決定關聯還沒有作者，因此不進圖。
- 分析包封面的時間與已確認比例，讓讀者知道這是某一刻的範圍，不是「整座系統已分析完成」。

## 14. Integration and Dependencies

- 舊系統資料庫是唯一的外部系統。v1 依賴它的目錄（表、欄、主鍵、外鍵、索引中與唯一性有關的資訊）以及有上限的列查詢。
- 不依賴客戶的文件管理系統、單一登入或票證系統。分析包是檔案，由林安自己附到升級案的文件裡。
- `[ASSUMPTION]` 不在 v1 讀取應用程式原始碼或預存程序來補強用途。依據只來自動詞彙表已列的觀察與分析師自填。

## 15. Risks and Mitigations

- **沒有外鍵的舊庫讓鄰居圖是單張表。** 緩解：FR-14 與待決定關聯在 v1 內；若第一座庫沒有外鍵，提前進 MVP（見第 6.2 節）。
- **起草把像真的句子寫進草稿，會議把草稿當成規格。** 緩解：FR-9 禁止自動已確認；FR-22 強制附上未確認清單；圖上不畫草稿用途。
- **範例含識別資料，經由分析包或外部起草外流。** 緩解：FR-23 預設遮罩；FR-18 外送開關預設關閉；封面標示未遮罩例外。
- **全庫一張圖被當成交付物，沒有人看得懂。** 緩解：預設鄰居圖與模組；超過 40 張的警告；SM-C2。
- **分析期間舊庫結構改變，字典對不上線上庫。** 緩解：FR-4 重新讀取保留結論並記錄消失與新增。
- **基數被讀成業務規則。** 緩解：父端固定為 `1` 且文件不宣稱「每筆子列都有父列」以外的業務不變條件；未明必須保持未明。
